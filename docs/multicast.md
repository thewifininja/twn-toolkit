# Multicast Tester

The Multicast Tester answers three different questions without requiring an
external traffic generator:

1. **Listen:** Is traffic for this IPv4 group and UDP port arriving on the
   selected interface, and what does the received stream look like?
2. **Send:** Can this toolkit host generate a controlled, sequenced multicast
   stream from a selected interface?
3. **End-to-end:** Does the toolkit host receive its generated stream through a
   different local interface, and how much loss, duplication, or reordering is
   visible?

Every run requires explicit authorization. Joins can change IGMP snooping state
on adjacent switches, and generated traffic consumes real network bandwidth.

## Listen mode

Choose the receiving interface, multicast group, UDP port, and observation
window. Any-source multicast (ASM) accepts any sender. An optional expected
source labels other senders in the report. Source-specific multicast (SSM)
joins a specific `(source, group)` channel when the operating system supports
`IP_ADD_SOURCE_MEMBERSHIP`; groups in `232.0.0.0/8` require SSM.

The receiver reports packet and byte totals, payload throughput, first-packet
delay, average and maximum interarrival gaps, interarrival standard deviation,
packet sizes, up to 100 source address/port pairs, and one-second traffic
buckets. While the socket is open, the page updates elapsed time, packet and
byte counts, achieved rate, observed sources, and the receive timeline without
blocking behind a loading screen. The run can be cancelled at any time. It does
not retain packet payloads.

The Quick setup list fills the standard IPv4 group and UDP port for mDNS,
LLMNR, SSDP/UPnP, and WS-Discovery. Both values matter: mDNS uses
`224.0.0.251:5353`, so listening to that group on the generic default port
will not receive mDNS datagrams. The selected receive interface must also match
the interface where a packet capture sees the traffic. The receiver enables
the platform's reusable-port socket option when available so it can coexist
with system services such as macOS `mDNSResponder`.

Choose the stream format that matches the traffic:

- **Generic UDP** works for any UDP payload and reports timing, volume, and
  sources. It cannot calculate exact loss or reordering because generic
  payloads do not contain sequence numbers.
- **RTP version 2** recognizes the fixed RTP header and reports SSRC, payload
  types, observed sequence gaps, duplicates, out-of-order packets, and
  RFC-style interarrival jitter. Set the RTP clock rate to the stream's actual
  media clock for a meaningful millisecond jitter value. Encrypted or
  nonstandard encapsulation may prevent header recognition.
- **TWN sequenced payload** recognizes streams generated by this tool and
  groups sequence statistics by the embedded session identifier.

## Send mode

Send mode emits a TWN test payload containing a session identifier, a 64-bit
sequence number, and a timestamp. Select the source interface, payload size,
rate, multicast TTL, DSCP, and optional source UDP port. Local loopback is off
by default and can be enabled only in standalone Send mode.

The fixed safety limits are:

- 1–300 seconds per run
- 64–9,000 bytes of UDP payload
- 0.01–200 Mbps of UDP payload or 1–50,000 packets per second
- no more than 1,000,000 scheduled packets per run

Payloads above 1,472 bytes may fragment on a normal 1,500-byte IPv4 path. A
successful Send result proves only that the local socket accepted the packets;
it does not prove that a receiver obtained them.

## End-to-end mode

End-to-end mode starts a receiver, waits for the group join, and then sends a
matching sequenced stream. It requires different send and receive interfaces
and disables multicast loopback so the ordinary local loopback copy cannot
produce a false success. The report compares sent packets with unique packets
from the matching session and shows loss, duplicates, and reordering.

This is useful on a dual-homed test host, but it is still influenced by that
host's routes, firewall, and socket behavior. For the strongest evidence, run
Send on one toolkit host and Listen in TWN mode on a separate toolkit host.
Neither arrangement identifies the exact switch or router where a stream was
dropped.

## Interpreting failures

A successful socket join proves that the host asked the operating system to
join the channel. It does not prove that IGMP snooping, queriers, PIM, reverse
path forwarding, TTL boundaries, ACLs, or multicast routing are correct.

When no data arrives, check:

1. The group, destination port, receiving interface, and SSM source. A packet
   capture should be filtered by all three destination fields, not only the
   multicast address.
2. Whether the source is actually sending and its multicast TTL reaches the
   receiver subnet.
3. Host firewall rules and local routes on both endpoints.
4. IGMP membership and snooping state on the access switches.
5. Querier, PIM neighbor, multicast route, RPF, ACL, and boundary state along
   the routed path.
6. A packet capture on the selected interface to distinguish host/socket
   behavior from an upstream delivery problem.

The downloaded JSON contains the same bounded report shown in the browser. The
activity dashboard retains counters only. Audit records retain the mode, scope,
membership, duration, result, and packet/byte counts—not group addresses,
source addresses, or payloads.
