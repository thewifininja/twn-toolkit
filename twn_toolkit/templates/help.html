Basics

Getting started

Back to contents
Navigation, Favorites, and finding tools

The persistent left pane is the primary navigation. Use Find a tool above Dashboard to filter permitted destinations by tool name or category path; clearing the search restores the tree exactly as you left it. Sections collapse independently, the current section opens automatically, and the pane scrolls separately from the page. Help and the installed version remain at the bottom. The hamburger button hides the pane completely when you want the full page width.

  • Favorites contains personal shortcuts. Hover or focus a tool and use its star to add/remove it. With two or more Favorites, drag the handle beside any item to reorder it, or focus the handle and use the up/down arrow keys. Changes save automatically, and the dashboard Quick launch follows the same order.
  • Fortinet Tools links to FortiGate and FortiAuthenticator profiles/workflows.
  • Network Tools groups vendor-neutral diagnostics under Addressing & Reachability, Services & Protocols, and Traffic & Interfaces.
  • Investigations keeps supported tool runs, notes, evidence, and an evidence-backed report together.
  • Automation separates the Automations workspace from the reusable Conditions and Actions libraries.
  • Administration contains Settings, Updates & Recovery, and System Diagnostics for system administrators.

On narrow screens, use the hamburger button to open or close navigation. The tool tree scrolls independently while Help, release notes, the configured instance name, and installed version remain reachable at the bottom. The sidebar follows the browser's visible viewport so Android browser controls and page zoom do not strand that footer off-screen.

First launch and service startup

There is no default login. A fresh installation generates a self-signed HTTPS certificate, prints its HTTPS URL, and the first visit creates the initial administrator. Review the browser's certificate warning before continuing. Rerunning the installer preserves an existing installation's protocol choice.

./install.sh
./twn start
./twn status
./twn service install
./twn service status

The service normally uses port 5050. Override one launch with TWN_TOOLKIT_PORT=8000 ./twn start.

./twn service install configures boot-time autostart through systemd on Ubuntu, Raspberry Pi OS, and other systemd Linux hosts, or through system LaunchDaemons on macOS. The toolkit, Gunicorn, automations, credentials, tools, and stored data run as the installing user. macOS additionally installs one bounded native connector that creates outbound TCP connections and blindly relays each stream as a root LaunchDaemon so Local Network Privacy keeps the complete flow in the exempt context. Authentication, commands, parsing, output handling, and storage remain in the unprivileged toolkit; the fixed relay does not parse, log, or persist traffic.

On a dedicated Linux diagnostic host, add --network-capabilities only when the service needs raw capture/replay, DHCP client-port access, promiscuous mode, or low-numbered listeners. The bounded unit capabilities are preferable to elevating the complete application. Verify both ./twn service status and ./twn status after installation and after a reboot.

On macOS, keep a service installation outside privacy-protected Desktop, Documents, Downloads, iCloud Drive, and ~/Library/CloudStorage locations. A path such as ~/twn-toolkit is suitable. The helper rejects protected locations before stopping the current toolkit; use a fresh clone or rebuild .venv after relocating an existing checkout.

Service uninstall removes only the systemd unit or LaunchDaemon property list. It retains instance/, Datastore files, profiles, certificates, captures, and logs for manual startup or later service reinstallation.

Shared interface conventions
  • Expandable cards contain saved definitions, editors, or result history.
  • New opens a form and changes to Cancel while open.
  • Secret fields are write-only and are not rendered back into forms.
  • Test/preview controls are read-only unless the page explicitly says changes will be applied.
  • Loading cards indicate server-side work. Automation workers continue without an open browser.
Workspace

Dashboard and activity

Back to contents
Quick launch, status, and recent work

The dashboard search finds permitted tools without leaving the page. Quick launch uses your Favorites in their saved order, then fills the available spaces with common diagnostics. Workspace status calls out live-monitoring errors, failed automations, and other items that may need attention.

Recent activity and the four-card snapshot answer what happened in the selected range. Open All activity metrics for every visible counter. Team activity appears only when there is more than one operator or contributor to compare.

Metrics and time ranges

Raw counters measure work performed: probes, replies, queries, frames, API calls, and completed tests. Activity score counts deliberate user executions; it does not imply remote success.

Use last hour, 24 hours, 7 days, 30 days, lifetime, or a custom local range. The range applies to widgets, rankings, and recent activity. Expand a scoreboard user to see all non-zero metrics.

Editing and resetting

Administrators can show, hide, and drag widgets into a global order. Hidden widgets move below the divider. Cancel restores the previous layout; Save persists it for all users. The layout can be backed up, but counters/history cannot.

Resetting a metric clears it globally. Clearing a user score resets only that user’s activity score and preserves their raw operational counters.

Administration

Accounts and access

Back to contents
Users and custom access profiles

System administrators create custom profiles and assign one or more to each operator. Effective access is the union of assigned profiles. Unauthorized tools disappear from navigation and remain blocked by the server if requested directly.

The built-in System administrator profile is protected. Assign it only to people who should manage users, profiles, backups, server access, and high-impact tools. Operators can use every tool granted by their assigned profiles without receiving unrestricted system administration.

Sessions, password policy, and recovery

Settings controls minimum password length, optional complexity, and idle timeout. Never disables idle expiration. If all administrators are locked out:

./twn stop
./twn adminreset
./twn start

This resets users only; saved device profiles and API keys remain.

Saved data

Profiles, secrets, and configuration backups

Back to contents
Saved profiles and credentials

Reusable lists and credentials reduce repeated entry across Fortinet, ping, DNS, RADIUS, SNMP, NTP, traceroute, TCP scanning, and automation tools. API keys, passwords, RADIUS secrets, and SNMP credentials are never rendered back into forms.

Compact Saved configuration panels use the same workflow throughout the network tools: choose a profile to load it, edit its working values, then save changes. Choose New / unsaved profile and enter a name to create one. Duplicate and Delete are available only while a saved profile is selected; changing its name renames it when saved.

Tools with several related record types use expandable profile libraries. Open a collection such as Credentials, Hosts, or Templates, use the in-flow New row to create a record, and expand an existing record to update, duplicate, or delete it.

Most profile stores are owner-readable local files, not a remote secrets vault. Automation action configuration and Remote Terminal credentials are encrypted at rest using the installation secret. Treat the host and instance/ as trusted and sensitive.

Configuration backups and import behavior

Select reusable groups in Administration → Updates & Recovery → Configuration backups. If any selection contains secrets, a backup password is mandatory; otherwise encryption is optional. Anyone with both the file and password can restore its secrets.

  • Inspect first: uploading validates the manifest and shows available groups, additions, matching names, and records Replace would remove. Nothing changes until the final confirmation.
  • Combine keeps local-only entries, adds new names, and updates matching names.
  • Replace makes supported selected groups match the backup. Groups that cannot be replaced safely are disabled in that mode.
  • Remote Terminal libraries require an explicit local-operator match, reassignment, or exclusion.
  • Wrong passwords or damaged files fail without importing partial plaintext. Supported stores roll back together if a later group fails.
  • Imported automations remain paused until reviewed.

Users and passwords, cases, issued certificate keys, automation history/output, dashboard counters, activity, scrollback, and Datastore files are not included. Use Recovery points for a complete matched code-and-instance restore, and portable case archives for investigations.

Profiles, permissions, and timeouts

Create and Test FortiGate/FortiAuthenticator profiles before running workflows. Use the least-privileged API administrator that permits the intended action. Test proves connectivity/authentication; HTTP 403 on a later operation usually means the remote profile lacks permission for that endpoint or write.

Unreachable appliances return after bounded timeouts rather than hanging indefinitely.

Exports, rename, reorder, and cleanup
  • Export workflows fetch managed AP, switch, wireless-client, switch-client, and related data into previews/CSV.
  • Rename workflows support CSV and interactive device loading. Every apply begins with a dry-run preview and requires explicit confirmation; completed, failed, and skipped changes remain distinguishable.
  • Re-order Managed FortiSwitches previews moves, requires in-page confirmation, and verifies final order.
  • FortiAuthenticator cleanup previews overlap before removing memberships or deleting MAC devices.
Wireless client history

The lookup normalizes MAC addresses, combines live state with local wireless event logs, and focuses on association-request events. Consecutive entries on one AP collapse; a roam creates the next visit. “No logs found” can mean memory logs are unavailable or old events rolled out. FortiAnalyzer is reserved for a future source.

Diagnostics

Network tools

Back to contents
Reachability, path, and service tools
  • Ping: live reachability, latency/loss charts, profiles, locked history, and CSV. Choose small, medium, or large graphs, or switch to the compact status grid for a fleet-wide healthy, degraded, and down view. The degraded definition uses editable rolling one-minute packet-loss, average-latency, and jitter thresholds; a failed latest probe is always down. Hover or focus a grid target to preview its recent graph, or tap it on a touch device. Pop out results opens the synchronized presentation in a separate resizable window while leaving configuration in the main workspace. Select Minimize to collapse an active run into the compact global Live tools footer dock. The dock starts collapsed; open it to rename a run with the pencil, select its card to restore it, or use × to stop it. The scheduler continues polling while you navigate and Restore reloads its bounded server-side history. Closing the toolkit lets the five-minute browser lease expire so an abandoned run stops automatically. Round interval controls desired start-to-start cadence; probe timeout controls how long a silent target may hold the round open. Rounds never overlap. Accelerated mode permits sub-second probe timeouts, which complete dense local-network checks faster but can classify slow replies as down. Recent samples remain detailed while older samples are summarized inside an adaptive browser-memory budget based on the active target count. The standard system ping compatibility engine supports up to 100 targets. A separately installed fping command must pass a real local ICMP capability check before the toolkit enables single-process batched rounds and the 250-target limit. Installation and updates never invoke a system package manager or sudo automatically.
  • Traceroute: UDP/ICMP traces to multiple targets with graphical and text output.
  • Path MTU: finds the largest unfragmented IPv4/IPv6 ICMP packet reaching a target.
  • TCP Port Scanner: checks authorized hosts against ports/ranges.
  • Certificate Inspector: shows the TLS chain and validates hostname, dates, order, and trust.
  • Certificate Automation: runs a guided Certbot DNS-01 workflow for Let's Encrypt or enrolls and rotates TLS server certificates through reusable Microsoft AD CS Web Enrollment profiles. ACME requests run in the background and wait for each TXT value, so the page may be left and reopened before validation continues. The propagation check compares the toolkit's configured resolver with the domain's authoritative nameservers, making stale recursive-cache answers visible. It remains advisory; keep all displayed TXT values published until issuance finishes. Generic DNS renewals repeat this guided process because the toolkit does not store DNS-provider credentials. The Microsoft AD CS workflow remains in Beta; its managed keys are encrypted locally. Certbot material is stored in owner-only directories with private-key mode 0600. HTTPS certificate verification defaults on for AD CS. Configuration backups may include reusable AD CS credentials, servers, templates, and managed definitions, but exclude every issued certificate, private key, and request-history record. Certificate downloads contain unencrypted private keys that require secure handling.
  • Wi-Fi/LAN Speed Test: browser-to-toolkit performance, not ISP speed.
  • iPerf3 Tester: uses an existing iperf3 system command; the toolkit never installs it. Client mode runs an authorization-confirmed TCP or UDP test for up to 60 seconds and 20 parallel streams, with forward/reverse direction and an explicit UDP target rate. Server mode provides explicit Start/Stop controls for a supervised multi-test listener on ports 1024–65535. It rejects busy ports before launch, accepts sequential clients independently of the page, appears in the owner’s dashboard and Live tools tray, and resumes with the toolkit until explicitly stopped. The newest 50 results are retained for the current user. Server results are collapsed by source IP and include sender/receiver throughput and transfer, TCP retransmits or UDP loss/jitter, interval data, CPU, and bounded raw iPerf3 JSON. Clear history removes the retained results.
  • Multicast Tester: listens for IPv4 any-source (ASM) or source-specific (SSM) multicast on an explicit interface, identifies observed sources, and streams live packet, byte, rate, source, elapsed-time, and one-second timeline telemetry with an immediate Cancel action. Quick setups fill the standard group and port for mDNS, LLMNR, SSDP/UPnP, and WS-Discovery; both values and the selected interface must match the captured traffic. In particular, mDNS is 224.0.0.251:5353. Reusable socket options allow the receiver to share standard ports with host services when the platform supports it. Generic UDP reports timing and volume; RTP mode adds SSRC, payload type, observed sequence gaps, duplicates, reordering, and RFC-style interarrival jitter; TWN payload mode recognizes the toolkit’s sequenced test packets. Send mode generates an authorization-confirmed stream with bounded payload size, packet/rate limits, TTL, DSCP, source port, and duration. End-to-end mode disables local loopback and measures matching-session loss and ordering from one host interface to another. Same-host results can be affected by local routing and filtering, so separate sender and receiver toolkit hosts provide stronger endpoint evidence. Joining a group does not by itself prove IGMP snooping, PIM, RPF, or upstream routing health. On macOS, PF enabled by VPN or security software may block the Router Alert option used by IGMP while still allowing the socket join. The page detects TWN's persistent compatibility configuration and provides ./twn multicast-pf status, install, and uninstall commands; privileged active-rule verification remains a Terminal operation. Link-local 224.0.0.0/24 traffic may appear healthy because switches normally flood it without learned membership. Reports can be downloaded as JSON.
Protocol and authentication tools
  • Ping: snapshots validated targets at Start; use Update targets to apply edits without clearing existing history. When a case is recording, Ping adds compact Start and Stop journal entries and retains the revision-aware sample history as CSV evidence. Individual timeouts do not flood the timeline, and a target that never replies is reported as “No replies observed” rather than declared down.
  • DNS: compares answers/timing across resolvers or runs an authorization-gated, evenly paced load test. Load tests are capped at 500 QPS per resolver, 30 seconds, five resolvers, 100 concurrent queries, and 50,000 total queries; results show achieved throughput, success rate, response types, and successful-query p50/p95/p99 latency.
  • SNMP: reusable v2c/v3 credentials, hosts, and OID collections. Build a monitor set of up to 20 standard IF-MIB interfaces across saved hosts and poll every 1–60 seconds. Each interface receives a compact filled graph with endpoint download (interface transmit) above a traffic-weighted zero line and endpoint upload (interface receive) below it. Hover a graph to inspect both rates at the nearest retained sample. Change the polling interval live, select a visible time range, and scroll through retained windows without stopping collection. The monitor prefers 64-bit counters, safely re-baselines after device or counter resets, and isolates polling failures by interface. Select Minimize to keep worker-side polling active in the Live tools footer dock; Restore reloads bounded server-side counter history without storing SNMP secrets in the live-session database.
  • Wake-on-LAN: sends one to five magic packets per saved or entered device through a selected IPv4 source interface. Local mode derives that interface's broadcast address; custom mode accepts a routed broadcast or configured WoL relay destination. Optional verification pings each configured hostname/IP until it responds or the bounded timeout expires. A successful send confirms only local UDP delivery—the remote router, relay, firmware, and power state determine whether the device receives and honors it.
  • RADIUS: PAP/CHAP plus decoded attributes; EAP methods require eapol_test.
  • NTP: compares offset, delay, jitter, stratum, identity, and sync health.
  • Syslog: sends RFC 5424 or listens for bounded UDP/TCP messages.
  • Webhook/API Tester: bounded HTTP requests without redirect following.
DHCP, bulk operations, and utilities
  • DHCP Discover: inspects Offers without requesting a lease. Linux binds UDP client port 68 and may need root or scoped service capabilities. macOS constructs the Discover and captures Offers through BPF so the normal-user service works with administrator-managed BPF access; it never binds privileged port 68.
  • Remote Terminal: offers temporary SSH or Telnet Quick Connect plus a private connection library with nested folders, reusable shared credentials, and credentials restricted to one saved host. A folder may assign a shared default credential; nested folders and hosts inherit the nearest assignment unless they override it or deliberately stop inheritance. Select mode reveals checkboxes only when requested, then atomically moves the selected hosts/folders or changes their shared/inherited credential behavior. Paste hosts or choose a CSV file to preview and atomically import up to 1,000 hosts into one destination folder; imported hosts inherit credentials by default and can be adjusted together afterward. The Connections explorer can be widened or hidden, and the terminal height can be adjusted; both preferences remain in that browser. Vault secrets are encrypted at rest and remain write-only in the browser. Telnet credentials are optional, are never submitted by prompt guessing, and remain server-side when provided; after the device prompts, the operator explicitly selects Send username or Send password. Telnet traffic, including credentials, is plaintext and should be limited to trusted legacy networks. A Quick Connect does not create a saved host or retain newly entered credentials; it may optionally use an existing shared vault entry. Pop out opens another view of the same owner-scoped terminal, so closing either browser view does not close the device connection. Restore active sessions from their tabs, recent history, or Live Tools with reconnect scrollback intact. Tabs can be renamed without changing their saved host, and their close control stops the terminal while retaining its scrollback in Recent sessions. Each operator may keep twelve active terminals, including multiple sessions to the same saved host; each terminal retains at most 10 MiB of output, stops after eight idle hours, and keeps completed scrollback for seven days. A toolkit restart cannot preserve an open TCP connection and marks the terminal interrupted. Terminal input is not logged separately, although device-echoed commands are remote output. Every new remote session automatically retains a sanitized transcript while a case actively records; paused cases receive no automatic terminal updates. Active or completed sessions can be attached to the current open case afterward. Operators with Datastore access can also save output independently as a live snapshot or completed scrollback without overwriting earlier files.
  • Bulk SSH: uses one spreadsheet-style target table with fixed Name and Host columns, editable variable columns, keyboard navigation, and multi-cell paste. Raw Matrix mode accepts pipe-, tab-, or comma-separated data for fast spreadsheet and CSV pasting. The compact host-list importer expands the existing Friendly Name = host syntax and inclusive IPv4/IPv6 ranges into editable table rows; imported rows may append to or replace the current rows without removing custom variable columns. Literal {{ '{{ variable }}' }} values can be used in reusable Stored Commandlets. A Commandlet can optionally save its target matrix, including hosts and custom values, so loading it restores a ready-to-edit run. Fleet runs support up to 5,000 targets and are submitted in batches of 50 with at most 10 simultaneous SSH connections; results appear after all batches finish. Credentials are always entered after the required signed per-host preview and are never stored. Use [timeout=600] command for a line-specific timeout; type \{{ '{{ variable }}' }} for literal braces. Results can be expanded or collapsed together and exported. A changed host identity shows readable saved and presented SHA-256 fingerprints instead of a raw key blob. After independently verifying a replaced or intentionally re-keyed device, the operator can re-enter credentials to replace the saved identity with that exact presented key and rerun only the affected host's signed command plan. The recovered result replaces the failed entry in place and is recorded separately when a case is active. Trusted older devices can use the separate per-run legacy SSH exception.
  • Bulk Transfer: fetches the same remote file list concurrently from named hosts over SFTP, SCP, or FTP. Choose a datastore folder for retained files or download a one-shot ZIP whose temporary server files are discarded. The default {timestamp}-{identity}-{filename} pattern can be customized with timestamp, host, friendly-label, identity, filename, stem, and suffix tokens. Duplicate names receive a numeric suffix; the ZIP also contains a transfer report. Unknown SSH host keys and legacy algorithms remain blocked unless each is explicitly allowed. FTP is plaintext and should be reserved for legacy targets.
  • Subnet Excluder: subtracts IPv4/IPv6 child networks.
  • What’s My IP?: shows the toolkit-observed client and attempts a browser-side public lookup.

Remote Terminal serial console: Quick Connect and saved connections can open attached USB, UART, and operating-system-paired Bluetooth serial devices with explicit baud, data-bit, parity, stop-bit, and flow-control settings. Saved records follow a stable adapter identity when the device path changes. A physical adapter can belong to only one active session at a time. Linux services commonly require their account to belong to the serial device's dialout group; restart the service after granting access.

Remote Terminal case capture: every new remote session automatically retains its transcript while a case is actively recording. Paused cases receive no automatic terminal timeline or evidence updates.

Investigations

Back to contents
Recording, pausing, and closing cases

Start a case before the first test. Each operator may participate in one recording or paused case, either as its owner or as an explicitly added collaborator. The global banner follows every participant across permitted toolkit pages, so their next supported result lands in the same shared journal. Notes, tool runs, and evidence remain attributed to the operator who added them; only the owner manages case state, membership, and report contents.

Pause recording suppresses new automatic tool events without ending the case. Deliberate notes and evidence uploads remain available while paused. Persistent tools attached while recording stay with that case so their eventual results are not orphaned. Close case first stops and retains attached Ping, SNMP monitor, packet-capture, iPerf3 server, and Remote Terminal sessions, then makes the journal and evidence read-only; starting the next case does not alter closed work.

Journal events and current tool support

The Journal retains meaningful actions in chronological order rather than page visits or unfinished forms. DNS Tester, TCP Port Scanner, Traceroute, NTP Tester, Path MTU Tester, Wi-Fi / LAN Speed Test, and Ping retain normalized targets, non-secret settings, outcomes, summary metrics, and bounded structured results. Ping uses lifecycle entries and generated CSV evidence instead of one entry per probe. A journal-write problem is logged without changing the diagnostic's own result.

Add operator notes for hypotheses, observations, calls, changes, and decisions that happen between tool runs. Paused cases accept notes because those additions are intentional.

Evidence and reports

Evidence uploads are stored beneath a managed Datastore/Investigations folder with collision-safe names. The library retains size, content type, collection time, and SHA-256 digest. Access is limited to explicit case participants; opening the underlying folder also requires Datastore access.

The case report is deterministic: a compact timeline links to separate detailed-result pages, followed by an optional evidence appendix. Use Report contents to include or exclude individual timeline entries and files; these presentation choices remain editable after the case closes and never delete source evidence. A closed case can be reopened in paused mode when no other case is open, preserving the close and reopen events in its journal. Download the generated PDF by itself, or download a case package containing that PDF, the selected original evidence, and a SHA-256 verification manifest.

For transfer between toolkit instances, Export portable case creates a complete .twncase archive with the full journal and every evidence file, independent of report inclusion. Import verifies the archive and evidence hashes, then creates a closed local copy owned by the importer. Original operator attribution remains visible, but source-instance users are not granted local access automatically.

To combine related work, open a closed source case and choose Review merge. The toolkit copies its complete journal and evidence into the open case you own while leaving the source unchanged. The review shows what will be copied or skipped; original attribution, event-to-evidence links, report choices, and evidence hashes are preserved. Case participants and permissions are never copied.

Host-side utilities

Local tools and datastore

Back to contents
Contained file management

The Datastore manages persistent files beneath instance/datastore/. Access is assigned like any other tool through custom profiles. Users can create and browse folders, upload multiple files, download files, rename entries, and delete files or empty folders.

Uploads are atomic and limited to 1 GiB per request. Existing names are never overwritten. The manager rejects traversal outside its root, does not follow symbolic links, and does not recursively delete populated folders.

Switch between list and grid layouts; the browser remembers the preference. A file's three-dot menu can open a safe, read-only plain-text preview or download the original. Text previews escape markup, replace undecodable UTF-8 sequences, and limit large files to their first 1 MiB.

Use the always-visible Select all control or select individual files and folders to reveal bulk download, move, and delete actions. Bulk downloads produce a ZIP with relative folder structure and empty folders preserved. Drag selected items directly onto a folder to move them. Non-empty folders cannot be deleted accidentally, and folders cannot be moved into themselves. The upload target accepts one or more files through the picker or desktop drag-and-drop. Bulk operations validate every source and destination before changing files.

Managed TFTP service

Local Tools → File Transfers contains managed TFTP, FTP, and authenticated SFTP/SCP listeners; outbound retrieval is available separately under Network Tools → Services & Protocols → Bulk Transfer. All listeners are disabled by default and remain contained beneath a selected datastore folder or one runtime-only file.

The SSH transfer listener defaults to 127.0.0.1:2022, stores only a password hash, rejects untrusted CIDRs before authentication, and never provides an interactive shell. SFTP and SCP, downloads, atomic uploads, overwrites, and incoming filename rewriting are independently controlled.

The TFTP root may be the datastore root or any saved subfolder. Alternatively, temporary mode serves one uploaded file that is erased whenever TFTP stops or restarts. Temporary mode is download-only.

The FTP listener has configurable control and passive port ranges, a one-way password hash, trusted-client CIDRs, total/per-client connection limits, atomic upload replacement, and the same incoming filename templates. FTP and SFTP/SCP reject inbound files beyond the datastore’s 1 GiB per-file ceiling. FTP does not encrypt authentication or file contents; prefer SFTP/SCP wherever possible.

Incoming uploads may keep {filename} or use a pattern such as {timestamp}-{client_ip}-{filename}. The {stem} and {suffix} tokens are also available. Custom naming stores files directly in the selected root; overwrite policy applies to the resulting stored name.

TFTP provides no authentication or encryption. Keep the trusted-client list narrow. Port 1069 works without elevation; binding standard UDP port 69 may require root or CAP_NET_BIND_SERVICE on Linux. The service supports binary RRQ/WRQ transfers plus block-size, timeout, and transfer-size negotiation.

Uploads are committed atomically after the final block. Existing files are rejected unless the administrator explicitly enables overwrite. Up to 20 transfers run concurrently. The latest 1,000 successful and failed transfers are visible in the datastore and can be cleared by an administrator.

Operational limits, diagnostics, and audit history

Administration → System Settings separates System, Email, Operations, and Accounts & access. System can follow the host timezone or save an explicit IANA timezone for human-facing automation timestamps without changing the host clock. Operational limits bound concurrent and queued automation runs, skip overlapping checks, cap datastore and automation-artifact usage, and preserve a configured amount of free disk.

Administration → System Diagnostics identifies manual versus boot-service operation, verifies the OS service manager separately from the managed process set, and reports the configured service account. It also reports web, supervisor, scheduler, and transfer-listener health; scheduler heartbeat age; disk and quota use; SQLite quick-check results; numbered migrations; reclaimable orphan artifacts; and the newest toolkit audit events. Live checks use bounded, read-only snapshots, so a busy database or service manager is called out without blocking the rest of the page. A SQLite file larger than 64 MiB is labeled manual instead of being scanned during page load; run its full integrity check during a maintenance window.

Command dependencies list the external executables used by supported workflows and distinguish optional integrations from baseline requirements. Platform capabilities are separate: on macOS, BPF readiness reflects whether the account running the toolkit can read and write a BPF device and notes whether Wireshark's optional ChmodBPF policy was detected; on Linux, diagnostics decode the current process's effective CAP_NET_RAW, CAP_NET_ADMIN, and CAP_NET_BIND_SERVICE grants. Finding tcpdump alone does not prove packet-capture permission.

The audit trail is role-neutral: meaningful, explicitly curated actions are recorded for operators and system administrators alike. It includes setup and sign-in outcomes, sign-out, saved-profile and credential lifecycle, connection tests, backups and exports, external device changes, operator-initiated tool runs, and administrative changes. High-frequency polling, raw speed-test transfer traffic, read-only discovery previews, theme changes, favorites, and other interface noise are omitted.

The audit ledger records the user, source address, endpoint, HTTP method, path, result code, and time. Expand a row to see the affected resource, selected event metadata, and before/after values. Profile events show whether sensitive configuration is present or was replaced without revealing its value. Tool runs retain bounded modes, counts, and outcomes rather than submitted targets, commands, payloads, packet bytes, captured messages, or returned data.

Referenced resources use human-readable names while retaining stable IDs for correlation. Datastore events identify affected paths, item types, file sizes, selections, and move destinations without retaining file contents. Fortinet and backup exports retain the selected profile or data groups and row counts, never the exported records.

Audit context is explicitly selected by each workflow and sanitized again before storage. Raw request bodies are never copied into the ledger; passwords, tokens, API keys, authorization headers, communities, private keys, and other secret-bearing fields are redacted recursively. Each authenticated event also identifies the actor role and assigned access profiles.

The supervisor restarts a failed scheduler or enabled transfer worker. Numbered toolkit migrations take a consistent SQLite snapshot before applying a new version.

Backups and future services

Datastore contents are operational files and are intentionally excluded from configuration backups. Use a complete recovery point or another deliberate datastore backup when those files matter.

TFTP and SSH-transfer settings/history are local operational state. Runtime-only staging is deliberately removed whenever its corresponding service stops.

Raspberry Pi networking

On device-tree-identified Raspberry Pi hardware, Administration → System Settings → Raspberry Pi networking can create a private NAT access point, bridge wireless clients to untagged Ethernet or an optional VLAN, or join an existing Wi-Fi network. Access-point modes appear only when NetworkManager reports an AP-capable Wi-Fi adapter and a wired interface.

Client mode supports open, WPA2 Personal, WPA2/WPA3 transition, WPA3 Personal, PEAP-MSCHAPv2, and EAP-TLS networks. PEAP validates the authentication-server certificate by default against the operating-system CA store or an uploaded CA and requires an expected server domain. Disabling that validation is an explicit unsafe exception. EAP-TLS accepts a PKCS#12 identity or a matching client certificate and private key. Passwords and keys are write-only, encrypted in the instance, and validated before use.

The web application never runs as root. On a Pi, sudo ./twn service install installs a root-owned NetworkManager broker that accepts only the configured service UID over a protected Unix socket. Preserve --network-capabilities when refreshing a service that already uses that option. Apply and Disable create a NetworkManager checkpoint and automatically restore the previous profiles, country, and radio state unless the administrator confirms reachability within two minutes.

Background work

Automations, schedules, conditions, and actions

Back to contents
The reusable four-part model
  1. An automation chooses manual, startup, condition, or schedule run mode and connects definitions to state policy and retained history.
  2. A schedule describes reusable calendar timing.
  3. A condition observes health and can participate in an ALL or ANY group.
  4. An action defines a trusted response in an ordered stage.

Use Automation → Schedules, Conditions, and Actions to maintain the reusable libraries. Use Automation → Automations to connect them, arm scheduled or monitored work, inspect checks, and manage retained runs.

Definitions may be shared by many automations. Editing a shared definition pauses every dependent automation for review. Use Duplicate when a new schedule, condition, action, or complete automation should begin as an independent copy; schedule rules and action-pipeline stages can also be duplicated while editing.

Run after host or toolkit startup

Startup mode can run once per operating-system boot (recommended) or after every complete toolkit start. Arming records the current event as a baseline, so setup never sends a surprise notification; the next matching startup creates one durable action job. Scheduler or worker restarts do not count as toolkit starts and cannot duplicate an already-recorded event.

The scheduler waits up to two minutes for DHCP or another usable IPv4/IPv6 address, then runs even if no address appeared. Use Test now to exercise the configured action without changing the armed startup baseline.

Webhook, Email, and Syslog templates can include {{ '{{toolkit.instance_name}}' }}, {{ '{{toolkit.hostname}}' }}, {{ '{{toolkit.version}}' }}, {{ '{{toolkit.primary_ipv4}}' }}, {{ '{{toolkit.ipv4_addresses}}' }}, {{ '{{toolkit.ipv6_addresses}}' }}, {{ '{{toolkit.primary_url}}' }}, {{ '{{toolkit.urls}}' }}, {{ '{{startup.reason}}' }}, and {{ '{{startup.occurred_at}}' }}. Exact JSON array variables retain their array type.

Monitoring policy and states
Check every
Desired start-to-start evaluation cadence; minimum one second. Rounds for one automation never overlap.
Trigger after
Consecutive met checks before actions fire once.
Recover after
Consecutive clear checks before rearming.
Cooldown
Minimum time between incident triggers.

Deadlines stay anchored to the configured cadence. If a timeout runs across the next deadline, the waiting round begins after the current one completes instead of being claimed and discarded. Long pauses resume from the current time without replaying a backlog. History timestamps identify when observation began, so a slow result remains associated with its intended round. Ping conditions support sub-second timeouts, such as 0.9 seconds, when the toolkit's accelerated fping engine is active; the compatibility engine retains a one-second minimum.

Monitoring moves through healthy, suspect, triggered, recovering, and healthy. Evaluation failures use error and do not count as a met condition. Manual/calendar triggers bypass debounce and recovery.

Parallel actions and sequential stages

Every automation begins with one stage. Actions inside a stage run in parallel; additional stages run sequentially from top to bottom after the previous stage finishes. Stages may be renamed and reordered, and an action can belong to only one stage in a pipeline.

Each stage controls whether the next stage runs: always; after success or partial success; only after full success; when one or more actions fail; or only when every action fails. A partial action completed some—but not all—of its internal work, so it is accepted by the success-or-partial route but not by full success or failure routes. This supports fallback paths such as trying Discord first and sending email only when Discord errors.

Every later stage may wait from zero seconds through 24 hours before starting. The prior stage's continuation rule is evaluated before the wait. Waiting is saved durably, releases the automation worker, survives a toolkit restart, and appears in scheduler status as Waiting between stages.

Webhook actions in later stages can use bounded, non-secret results from earlier stages through {{ '{{actions.results}}' }}, {{ '{{actions.successful}}' }}, {{ '{{actions.partial}}' }}, and {{ '{{actions.failed}}' }}. Raw SSH command output is retained for download but is not automatically exposed to notifications.

ICMP, DNS, and TCP conditions

Ping treats every target as a check. Add one to ten probes per evaluation to apply packet-loss, average-latency, and jitter limits; existing reachability-only conditions remain compatible. Test displays every target's reachability, quality metrics, elapsed time, and policy outcome.

DNS Lookup queries each name through each resolver, supports A/AAAA/CNAME/MX/NS/PTR/TXT, and optionally requires any/all expected answers. DNS Performance uses the same matrix to trigger on failures or response-time thresholds. Tests show every resolver path and timing.

TCP assigns ports per host:

Home FortiGate = gate.example.com | 8443
Google = google.com | 443
Core Switch = 10.0.0.10 | 22, 443, 8000-8010

Expected open requires a connection. Expected closed requires explicit refusal; timeout does not prove closed.

SNMP OID value conditions

SNMP conditions reuse hosts, credentials, and individual OIDs from collections managed in SNMP Tester. Credentials remain in their existing write-only profile store.

Select target hosts once, then add up to 20 named rules. Text rules support equality and containment with optional case sensitivity; numeric rules support inclusive or exclusive upper/lower thresholds. An unavailable-value rule detects failed or empty polls.

Rules use AND logic on each host. A host matches only when every rule matches on that same host, so high CPU on one switch cannot combine with high memory on another. The final threshold requires one, a selected number, or all hosts to match the complete rule group.

Walk rules match when at least one returned value matches. Test results summarize every host and its rule outcomes.

OID profiles can expose reusable calculated values:

Current Memory KB = 1.3.6.1.4.1.example.1.0
Total Memory KB = 1.3.6.1.4.1.example.2.0
calc: Memory Usage % = percent(Current Memory KB, Total Memory KB)

Supported functions are percent(A, B), remaining_percent(A, B), difference(A, B), and sum(A, B). Inputs must resolve to scalar numeric GET values. Unknown labels, circular dependencies, walked inputs, missing/nonnumeric values, and division by zero are rejected or reported.

Certificate health conditions

Monitor up to 20 TLS endpoints with optional friendly names and custom ports:

Home FortiGate = gate.example.com | 8443
Public Portal = portal.example.com | 443

Connection failures, expired certificates, and not-yet-valid certificates always fail. Configure an expiration warning from 0 to 3650 days, and optionally require hostname/IP SAN matching, validation through the toolkit server’s system trust store, and a correctly ordered chain with no likely missing intermediate.

Disable the optional trust, name, or chain policies when monitoring intentional private/self-signed infrastructure. Test results show the endpoint, common name, expiration horizon, TLS version, timing, and every policy failure reason.

Manual and scheduled automations

Manual mode runs only when an administrator selects Run now. Reusable Calendar schedules contain up to 50 one-time, daily, weekday, every-N-weeks, monthly-date, or ordinal-weekday rules with an explicit timezone.

Missed occurrences may run late, run only within a grace period, or skip. Refresh next run time is read-only. Simultaneous rules collapse into one occurrence.

SSH collection action

Runs a variable-aware command template against a spreadsheet-style matrix of up to 5,000 hosts and retains per-host output. Use fixed Name and Host columns plus custom variable columns, or load a Stored Commandlet to copy its commands, timeout, and optional targets into the action. The action keeps its own snapshot so later Commandlet edits do not silently change an armed automation.

Fleet execution uses batches of 50 with at most 10 simultaneous SSH connections. Completion is the return of the original device prompt. Default ceiling is 300 seconds; override one command:

[timeout=600] diag debug report

Overrides are 1–3600 seconds with a one-hour combined budget per host. Timeouts retain partial output and stop later commands only on that host.

SSH file collection action

Fetches up to 200 host/path combinations over SFTP, SCP, or FTP using write-only credentials. Use Friendly Name = host targets and the same token-based filename patterns as Bulk Transfer. SFTP/SCP encrypt traffic; FTP does not.

Collected action run retains successful files beside the run and adds them to Download ZIP without placing them in the datastore. Datastore persists files beneath a selected folder and can create one friendly-name/host subfolder per target. Cross-run filename collisions receive a numeric suffix rather than overwriting.

Retained binary files are stored outside SQLite under instance/automation_artifacts/. Deleting, clearing, or retention-pruning a run deletes its artifact directory too.

Syslog notification action

Sends RFC 5424 to up to 20 UDP/TCP collectors:

Primary SIEM = syslog.example.com | 514
Backup collector = 192.0.2.20 | 5514

Messages support trigger, timestamp, and the documented {{ '{{toolkit.*}}' }}/{{ '{{startup.*}}' }} identity variables. Use {{ '{{timestamp.display}}' }} for a human-readable toolkit-local value or {{ '{{timestamp.local}}' }} for ISO format with an offset; the existing {{ '{{timestamp}}' }} remains UTC. UDP success means the local socket accepted the datagram, not remote acknowledgment.

Webhook / API notification action

Sends one POST, PUT, or PATCH template to up to 10 HTTP/HTTPS endpoints. Endpoints may use Friendly Name = URL. Configure accepted status values/ranges, timeout, TLS verification, body format, and write-only headers.

Accepted statuses count as success; every other response counts as failure. You may configure one to five attempts, an initial retry delay, and retryable statuses such as 408,425,429,500-599. Network failures and selected statuses use exponential backoff capped at 60 seconds; other failures stop immediately. One attempt is the default because a retry can duplicate a notification when the receiver processed the first request but its response was lost. Each endpoint's attempt history is retained with the run.

JSON templates are parsed before substitution, so exact trigger, prior-action, address-list, and URL-list variables retain boolean/object/list types. Text and JSON templates also support the toolkit and startup identity variables documented above. New templates use the toolkit-local ISO timestamp and include {{ '{{toolkit.timezone}}' }}; existing saved payloads are never rewritten. Redirects are reported but not followed; retained response previews are capped at 4 KiB per endpoint.

Authorization/API-key headers are encrypted, never rendered back into the editor, and never copied into retained run output. Leave the field blank to keep saved headers, or select Remove all saved headers while updating.

Email notification action

Sends a plain-text message through the installation-wide SMTP service configured under Administration → System Settings → Email. Configure To, optional Cc/Bcc recipients, a subject, and a message template using the same trigger, prior-action, toolkit, startup, and localized timestamp variables available to webhooks.

SMTP supports STARTTLS, implicit TLS, or explicit plaintext delivery, with certificate verification enabled by default. The optional SMTP password is encrypted and write-only. Use the settings-page test before arming an email automation.

Email is metadata-only: the toolkit never adds collected files or PCAP attachments. Retained results contain per-recipient delivery status, subject, and message ID, but not the rendered message body.

Packet capture action

Starts the same bounded local tcpdump capture available in Network Tools when an automation fires. Select a local or SPAN-connected interface, optional BPF filter, duration, packet count, file-size ceiling, snapshot length, and promiscuous-mode policy.

Choose whether the PCAP is retained as a binary automation artifact for Download ZIP or saved directly beneath a selected Local Datastore folder. Filename patterns support {timestamp}, {action}, and {interface}; duplicate names receive a numeric suffix. The capture begins after the triggering condition is detected, so it does not include packets from before detection. A retry may create another PCAP because automation action delivery is intentionally at least once.

History, downloads, cleanup, and scheduler

Checks, triggers, action status, and structured retained output live in instance/automations.sqlite3; run-retained binary artifacts live in instance/automation_artifacts/. SSH ZIPs contain timestamped host files, SFTP/SCP ZIPs include retained fetched files, and notification ZIPs contain delivery JSON. Delete run removes one result and its run artifacts but does not delete files saved to Local Datastore; Clear collected data removes action runs but preserves condition history.

Administration → System Settings → Operations controls global retention. Check records default to 7 days; collected action runs default to never expire. Use 0 for indefinite retention. The card previews eligible records, supports an immediate policy-based prune, and reports database size and oldest records.

The scheduler prunes at most once daily. Optimize database is a separate manual action that reclaims unused SQLite file space and may briefly pause automation writes.

./twn start launches one scheduler beside the web service. Work and delayed-stage countdowns continue without a browser. Imported automations remain paused.

DHCP Discover

Probe boundary and results

Choose one local interface, an authorized unicast client MAC, a 0.2–15 second timeout, and an ordered Parameter Request List. Optional host-name and vendor-class values help exercise client-specific policy. Each run creates a new transaction identifier and sends exactly one broadcast Discover.

The toolkit accepts only matching Offers, deduplicates repeated server/address pairs, and displays the offered address, server identifier, packet source, relay and next-server fields, plus decoded and raw option values. It never sends a Request, accepts a lease, or changes local addressing, routes, or DNS.

Platform permissions and no-response checks

Linux binds UDP client port 68 and can use ./twn service install --network-capabilities. macOS instead opens its BPF listener first, transmits one Ethernet/IPv4/UDP Discover through Scapy/libpcap/BPF, and captures matching Offers without a privileged port bind. Grant persistent BPF read/write access to the normal LaunchDaemon account; do not elevate the whole web application.

No matching Offer proves only that none reached this run before timeout. Verify interface/VLAN selection, test-MAC and vendor policy, DHCP relay behavior, local firewall or endpoint security, AP/switch broadcast handling, timeout, and the service account's packet permission. A simultaneous packet capture distinguishes an absent reply from a host-capture problem.

Passive diagnostics

Packet Capture

Back to contents
Standalone captures and SPAN interfaces

Packet Capture runs tcpdump on an interface local to the toolkit server. A common deployment connects a secondary server interface to a managed switch SPAN or mirror destination while the primary interface remains dedicated to toolkit management and active health checks.

Choose an interface, optional BPF filter, duration, packet limit, maximum file size, snapshot length, and promiscuous mode. The first reached limit stops the capture. Recent captures stay collapsed by default while retaining interface, time, size, packet count, and status in the summary; active or focused captures open automatically. The background worker continues after navigation, and an expanded capture can be stopped, downloaded, saved to Local Datastore with a custom filename, or deleted.

Open the floating viewer during or after capture to see bounded source and destination MAC/IP/port, protocol, VLAN, timestamp, and length summaries without payload contents. It can be moved or minimized, restores across navigation, and auto-scrolls with incoming packets by default.

Local Datastore shows Inspect PCAP in the file actions for .pcap, .pcapng, and .cap files, so retained files can invoke the same viewer without returning to Packet Capture.

Permissions, storage, and sensitive traffic

The toolkit service account must be allowed to capture packets. Prefer the scoped Linux service capabilities or persistent administrator-managed macOS BPF read/write access for the normal service account instead of elevating the full application. Wireshark's optional ChmodBPF service is one established macOS policy. The page reports missing tcpdump; a permission problem appears as a failed capture with the exact safe error.

Only one capture may run on an interface at a time across standalone and automation use. Standalone and automation PCAPs share the configured automation-artifact quota and minimum free-disk reserve. Datastore copies follow the separate datastore quota and remain after capture-history deletion. PCAPs may contain credentials and payload data, are excluded from configuration backups, and should be deleted when no longer needed.

Packet Replay

Inputs, rewrites, VLANs, and sending

Transmit raw Ethernet frames from hex, a local classic-PCAP upload, or a compatible .pcap/.cap file selected directly from Local Datastore. Stored capture selection requires both Packet Replay and Datastore access; administrators have both automatically. Select the wired interface, review decoded fields and the rewrite plan, then explicitly confirm authorization before sending from Preview. A replay is limited to a 256 KiB source capture, 10,000 emitted frames, and five minutes of scheduled duration. Multiple source packets, repeat, interval, and MAC/IP/port rewrites are supported.

VLAN fanout accepts IDs, ranges, and untagged: untagged,10-12,20. VLAN 0 is priority-tagged, not untagged.

Permissions and capture verification

Linux needs raw packet access; ./twn service install --network-capabilities provides the bounded service policy. macOS uses Scapy/libpcap/BPF and should grant persistent BPF read/write access to the normal LaunchDaemon account. Do not elevate the full web application merely for replay. Wireless 802.11 injection is unsupported.

sudo tcpdump -i en0 -e -nn -vvv 'vlan or ether proto 0x8100'
sudo tcpdump -i en0 -e -nn -vvv 'vlan and port 514'

Sender acceptance is not remote delivery; verify actual egress on the wire.

Link-layer testing

LLDP Lab

Back to contents
Observe and preserve neighbors

Observe asks the host lldpd service to decode LLDP received on each local interface. It displays chassis and port identity, management addresses, capabilities, VLAN information, and LLDP-MED policy when the neighbor advertises those fields. A snapshot can be retained as timestamped JSON evidence while a case actively records. Observation is passive, but its completeness depends on the interface, driver, neighboring device, and lldpd control-socket access available to the toolkit service account.

Emulate a standards-based endpoint

Emulate constructs and transmits an exact Ethernet LLDP frame on one selected interface. Start with the generic endpoint, phone, switch, or experimental FortiSwitch baseline; then customize identity, advertised capabilities, management address, PVID, LLDP-MED endpoint class and voice policy, and bounded organizational TLVs. Preview the complete TLV list before explicitly confirming authorization. Saved personas are reusable and can be duplicated.

Only one LLDP Lab session may transmit on an interface at a time. Sessions are limited to 1–60 minutes with a 1–120 second interval and send a TTL-zero shutdown PDU when they stop normally. By default the worker temporarily suppresses lldpd transmission on that interface so the host identity and emulated identity do not compete; reception remains enabled and the previous port state is restored at the end.

The phone preset advertises standards-based LLDP-MED fields suitable for testing voice-policy assignment. The FortiSwitch preset is an experimental starting point: vendor discovery and secure FortiLink/Auto-ISL behavior may require additional proprietary state, certificates, or protocol exchanges beyond a static LLDP advertisement. Verify the switch's actual response rather than treating transmitted frames as proof of a completed workflow.

Installation, permissions, and verification

Install and run lldpd on the toolkit host for decoded observation. Linux service installations need ./twn service install --network-capabilities for the scoped raw-frame transmission path. macOS uses Scapy/libpcap/BPF and needs persistent BPF read/write access for the normal LaunchDaemon account. Do not elevate the full web application.

sudo tcpdump -i eth0 -e -nn -vvv 'ether proto 0x88cc'
lldpcli -f keyvalue show interfaces ports eth0

Capture the emitted PDU and inspect the adjacent switch's learned neighbor, VLAN, and port state. Sending a valid advertisement proves only local egress; it does not prove that the switch accepted or acted on every advertised field.

On a dedicated Linux diagnostic host, ./twn service install --network-capabilities grants the service only CAP_NET_RAW, CAP_NET_ADMIN, and CAP_NET_BIND_SERVICE for capture, replay, interface access, and low ports. The default service has no added capabilities. macOS uses its UID-restricted TCP connector for Local Network Privacy while the normal service account still needs separately provisioned BPF access for packet capture, replay, and DHCP Discover. Wireshark's optional ChmodBPF service is one established way to grant its access_bpf group persistent BPF read/write access.

With autostart installed, ordinary ./twn stop and ./twn start pause and resume the managed processes through the loaded coordinator. On macOS, v0.16.10 installs the protected TCP connector plus direct unprivileged LaunchDaemons for web, automation, supervisor, and transfer workers. Existing macOS service installations must run sudo ./twn service install once after the code upgrade to install that root-owned connector and its property list. During an upgrade or rollback, the updater first validates the replacement process set and finalizes its status and cleanup. Only then does systemd or launchd reload twn from disk. This keeps the updater alive through completion, emits the toolkit-start automation event only for the final managed start, and needs no recurring administrator prompt. A reboot always starts the toolkit again. Installing the OS service does not enable disabled TFTP, FTP, SFTP/SCP, or iPerf3 listeners.

HTTPS and self-signed certificates

Fresh installations use HTTPS by default; upgrades preserve their existing protocol. Run ./twn enable-https to migrate an older HTTP installation and safely restart the toolkit. Add stable names or addresses when needed: ./twn enable-https toolkit.local 192.0.2.25.

The certificate includes localhost, loopback, and detected machine names. Browsers warn until the certificate is trusted. HTTPS enables secure session cookies, and ./twn status prints the active HTTPS URL.

The owner-only private key lives at instance/tls/key.pem and is not included in configuration backups. Run ./twn disable-https to restart over HTTP without deleting the certificate. Externally managed PEM files may be supplied with both TWN_TOOLKIT_CERTFILE and TWN_TOOLKIT_KEYFILE.

Administration → System Settings → System can define a short instance name, preferred FQDN, and toolkit timezone. Validation checks DNS-name and IANA-timezone structure but never performs a lookup. The short name appears in browser titles and the sidebar; the FQDN is used in launcher URLs. The timezone controls localized automation variables and new schedule defaults without changing the host clock, stored UTC records, or saved schedules. Explicitly select certificate regeneration while saving when the toolkit-managed certificate should include the new identity.

Upgrade, verify, and roll back

Administration → Updates & Recovery checks the official stable release channel without requiring Git, the GitHub CLI, or manual tags. It downloads only releases carrying the toolkit ZIP and SHA-256 assets, then validates the whole bundle and every internally manifested file. An official bundle may also be uploaded manually when the release API is unavailable.

An installation running v0.10.2 or older needs one final conventional upgrade to v0.11.0, the first updater-enabled release. After that transition, use this page or the matching CLI commands for every release.

Before changing application files, the updater stops all services and creates an owner-only recovery point containing matched application code and the complete stopped instance/. It verifies the installed version, managed processes, enabled services, and every SQLite database. Failed validation automatically restores and revalidates the previous matched pair. On a boot-managed host, launcher reload is deferred until that validation, terminal status, audit record, and cleanup are complete; the final systemd or launchd start then records exactly one toolkit-start automation event.

Use ./twn upgrade, ./twn backup, ./twn upgrade-status, or ./twn rollback RECOVERY_POINT_ID when the web interface is unavailable. Rollback replaces both code and instance data; the toolkit never runs older code against post-upgrade data. Five recovery points are retained beneath owner-only .twn-upgrades/backups/.

Port conflicts and sudo ownership

Run ./twn recover when a failed restart leaves the configured port occupied or a sudo launch leaves a root-owned server. Recovery detects Linux or macOS, verifies the listener belongs to this installation, requests elevated access only when needed, repairs instance/ and updater metadata ownership, and starts normally. It will not terminate an unrelated listener.

Use ./twn fix-permissions when only runtime ownership needs repair.

Common checks
  • Restart after code/dependency updates.
  • Verify both web and scheduler with ./twn status.
  • Inspect ./twn logs.

Responsibility

Security, local data, and disclaimer

Back to contents
Deployment boundary and retained data

This is local-first software for a trusted workstation/internal network, not direct internet exposure. Use TLS and an appropriate access layer across untrusted networks. Server access settings can allow explicit addresses/CIDRs; loopback remains allowed.

User passwords are scrypt hashes; sessions use a separate secret. Profile stores and automation databases live under owner-only ignored instance/ paths. Protect the host, filesystem backups, exported backups, downloads, and browser session.

SSH compatibility and dependency advisories

SSH and SFTP/SCP reject legacy SHA-1 ssh-rsa host and user keys by default. Prefer upgrading the remote device or adding a modern key. For a trusted older device, enable Allow legacy SSH algorithms on that Remote Terminal, Bulk SSH, or Bulk Transfer connection. The same option is available on saved SSH/SFTP/SCP automation actions and the managed SFTP/SCP service; those persistent exceptions stay active until disabled. Legacy compatibility enables weaker algorithms still supported by the installed SSH library and is independent of accepting unknown host keys. Its use is audit-visible.

TWN_ALLOW_LEGACY_SSH_RSA=true remains an emergency global compatibility override. It affects every SSH client and server path for the life of the process, so prefer the narrower UI controls and remove the environment override promptly.

Release CI audits every pinned runtime dependency. Any advisory that cannot yet be fixed upstream must have a narrow documented mitigation showing why the affected feature is disabled or unused; new or expanded exposure blocks release.
